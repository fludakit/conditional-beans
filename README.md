# Conditional Beans for CDI

A portable CDI Extension that enables a bean **only when a condition matches the current deployment**.

- Target runtime: **CDI 4.1** (`jakarta.enterprise:jakarta.enterprise.cdi-api:4.1.0`)
- Verified on **Weld 6.0.3.Final** with **Weld JUnit5**
- Core API: **three types** - `@Conditional`, `Condition`, `ConditionContext`
- Repeatable support: **one container** - `@Conditionals`, generated by the compiler
- Two runtimes: **CDI Full** (portable extension) and **CDI Lite** (build compatible extension)
- No runtime dependency beyond the CDI API

This is a working prototype for the Jakarta EE CDI issues
[jakartaee/cdi#869](https://github.com/jakartaee/cdi/issues/869) and
[jakartaee/cdi#986](https://github.com/jakartaee/cdi/issues/986).

## Quick start

Add the artifact to the deployment and declare a condition on a bean. For example, enable a bean only on supported operating systems by reading the `os.name` system property:

```java
public class SupportedOsCondition implements Condition<Conditional> {

    @Override
    public boolean matches(ConditionContext context, Conditional annotation) {
        String osName = context.getProperty("os.name").orElse("").toLowerCase();

        boolean isWindows = osName.contains("win");
        boolean isMac = osName.contains("mac");
        boolean isLinux = osName.contains("nux") || osName.contains("nix");

        return isWindows || isMac || isLinux;
    }
}
```

```java
@ApplicationScoped
@Conditional(SupportedOsCondition.class)
public class NativeService implements Service {
}
```

When the current OS does not match, the bean is **not part of the deployment**: it is not injectable, it does
not show up in `BeanManager.getBeans(...)`, and it produces no `ProcessBean` event. An injection point that
requires it fails the deployment with an unsatisfied-dependency error, making missing beans explicit.

The extension is registered through `META-INF/services/jakarta.enterprise.inject.spi.Extension`, so it is
active in every deployment that has the artifact on the classpath.

## The API

### `@Conditional`

```java
@Documented
@Retention(RUNTIME)
@Target({ TYPE, METHOD, FIELD, ANNOTATION_TYPE })
@Stereotype
@Repeatable(Conditionals.class)
public @interface Conditional {
    Class<? extends Condition<?>>[] value();
}
```

Applicable to a bean class, a producer method and a producer field.

**The annotation is repeatable**, so several conditions can be declared on one element, one annotation each:

```java
@ApplicationScoped
@Conditional(SupportedOsCondition.class)
@Conditional(DatabaseAvailable.class)
public class NativeService implements Service {
}
```

The array form carries the same meaning, and the two styles may be mixed - `@Conditional({ A.class, B.class })`
and two separate `@Conditional` annotations are collected together, and all of them have to match. A condition
declared on a **stereotype** is collected in addition to the ones declared on the bean, which is why a
stereotype may add its own requirements without interfering with the bean.

The repeatable mechanism needs a container annotation, `@Conditionals`, which the Java compiler
generates and fills. It is not meant to be used directly, and it stays invisible in the deployment: the
container reports the same stereotypes as the plain annotation does.

The naming follows the convention for a repeatable annotation. Jakarta Persistence, Jakarta EJB and
Jakarta JMS declare a top-level container in the plural form - `@NamedQueries`, `@Schedules`,
`@JMSDestinationDefinitions` - and the CDI specification shows the same pattern for a repeating qualifier,
with `@Location` and `@Locations`. Spring Framework and Micronaut follow it too, with `@ComponentScans`,
`@PropertySources`, `@Schedules`, `@Requirements` and `@QueryHints`. The nested `List` container is the
alternative shape, used by Jakarta Validation, Jakarta Data and Micronaut. The proposal section below lists
the precedents.

The annotation is itself a **CDI stereotype** and may be used as a meta-annotation, which is how an
application composes an annotation of its own. See "Composed annotations" below.

All collected conditions have to match. The first one that does not match vetoes the bean.

### `Condition`

```java
@FunctionalInterface
public interface Condition<A extends Annotation> {

    boolean matches(ConditionContext context, A annotation);
}
```

A condition is a plain class with a no-argument constructor. It is **written against the annotation that
declares it**, so that it can read the values of that annotation without reflection:

```java
public class BrazilCondition implements Condition<ConditionalOnCountry> {

    @Override
    public boolean matches(ConditionContext context, ConditionalOnCountry annotation) {
        return "BR".equals(context.getProperty(annotation.country()).orElse(null));
    }
}
```

The type argument decides which annotation the condition is handed:

| The condition is written as | It is handed | The condition was declared by |
|---|---|---|
| `Condition<Conditional>` | the `@Conditional` annotation | `@Conditional(X.class)` on the bean |
| `Condition<ConditionalOnProperty>` | the `@ConditionalOnProperty` annotation | `@ConditionalOnProperty(...)` on the bean |
| `Condition<MyOwnAnnotation>` | the `@MyOwnAnnotation` annotation | an annotation of the application that carries `@Conditional` |

The choice is made by the type of the condition, so it is checked by the compiler and it stays consistent
for the direct form, the meta-annotation form, the stereotype form and the repeatable form.

**The container instantiates the condition directly, never through CDI.** At evaluation time the container
cannot inject anything, so a condition reaches deployment state through `ConditionContext` rather than
through injected beans. A condition must therefore be side-effect free and deterministic for a given
deployment.

### `ConditionContext`

```java
public interface ConditionContext {

    Optional<String> getProperty(String key);

    boolean hasClass(String... className);

    @SuppressWarnings("unchecked")
    boolean hasBean(Class<?> beanClass, Class<? extends Annotation>... qualifiers);
}
```

The context exposes only the deployment data needed at bootstrap/build time:

| Method | Meaning |
|---|---|
| `getProperty(String)` | Returns a configuration property value (typically system properties, then environment variables; dotted keys may also resolve relaxed env names such as `app.country` → `APP_COUNTRY`). |
| `hasClass(String...)` | Checks whether all named classes are available to the deployment. |
| `hasBean(Class<?> beanClass, Class<? extends Annotation>... qualifiers)` | Checks whether a matching bean is part of the potential deployment model (independent of declaration order; a bean vetoed by a condition may still count as present for evaluation). |

## Built-in conditions

The package `io.github.fludakit.conditional.full.builtin` carries the conditions that most applications need.
They follow the Spring naming, and each of them has a counterpart that inverts it.

| Annotation | The bean is enabled when |
|---|---|
| `@ConditionalOnProperty(name, havingValue)` | the named configuration entry is present and, when `havingValue` is given, has that value |
| `@ConditionalOnMissingProperty(name)` | every named configuration entry is **not** configured |
| `@ConditionalOnClass(name)` | every named class is on the classpath |
| `@ConditionalOnMissingClass(name)` | every named class is **not** on the classpath |
| `@ConditionalOnBean(value)` | every named type has a bean |
| `@ConditionalOnMissingBean(value)` | every named type has **no** bean |

```java
@ApplicationScoped
@ConditionalOnProperty(name = "app.country", havingValue = "BR")
public class BrazilTaxCalculator implements TaxCalculator {
}

@ApplicationScoped
@ConditionalOnMissingClass(name = "com.example.LegacyIntegration")
public class ModernIntegration {
}
```

They can be used on a bean class, a producer method, a producer field and a stereotype, and they compose
with a condition that is written by hand.

**The class conditions take class names, not classes.** This is a deliberate difference from Spring. In CDI
an annotation that refers to a class that is not on the classpath cannot even be read: the annotation
instance is created, but reading the attribute throws `TypeNotPresentException`. A name is resolved
without loading the class, so `@ConditionalOnClass(name = "com.example.Optional")` is the only form that
works for an optional dependency. The same applies to a condition of your own that tests for a class that
may be absent - use `ConditionContext.hasClass(String)`.

**`@ConditionalOnProperty` takes one entry.** `name` is a single entry and `havingValue` is the value it
has to have, compared ignoring the case. An empty `havingValue` - the default - accepts any value, so the
annotation asks for the presence of the entry and nothing more. The entries that are not required are covered
by `@ConditionalOnMissingProperty`, which takes a list of names.

**`@ConditionalOnBean` and `@ConditionalOnMissingBean`** evaluate against the potential bean set of the deployment via `ConditionContext.hasBean(...)`. A bean vetoed by a condition may still count as present for evaluation, and matching can include qualifier types when specified by the annotation.

## Composed annotations

`@Conditional` is itself a **CDI stereotype**, and it may be used as a meta-annotation. An application can
therefore declare an annotation of its own that carries a condition, the way Spring does:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Conditional(SupportedOsCondition.class)
public @interface SupportedOs {
}

@ApplicationScoped
@SupportedOs
public class NativeService implements Service {
}
```

The condition is found through the annotation that declares it, so it applies to every bean carrying that
annotation. The same works for a stereotype, and the built-in conditions can be used that way as well:

```java
@Stereotype
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@ConditionalOnMissingProperty(name = "app.legacy")
public @interface WithoutLegacy {
}
```

A bean may carry a composed annotation **and** a condition of its own. Both are evaluated, and the bean is
enabled only when every one of them matches.

Because `@Conditional` is a stereotype, the container itself takes part: `Bean.getStereotypes()` reports
it, and a stereotype that declares `@Conditional` inherits it. That is the CDI counterpart of the
meta-annotation mechanism of Spring, and it keeps the mechanism inside the concepts of CDI.

## The two runtimes

### CDI Full

The portable extension observes `ProcessBeanAttributes`, which is the only portable point at which a bean
can still be removed from the deployment, and vetoes the bean when one of its conditions does not match.

The set of beans that could be part of the deployment is collected from the `ProcessAnnotatedType` events,
which the container fires for every discovered type before it fires the first `ProcessBeanAttributes`. The
model is therefore complete before the first condition is evaluated, and the answer never depends on the
order in which the beans are declared.

### CDI Lite

A CDI Lite container has no portable extension API. The `lite` module is therefore a **build compatible
extension**, which evaluates the conditions while the application is built:

1. the **enhancement** step sees every class of the deployment, one class at a time, and evaluates the
   conditions of the class and of its producers. A class whose condition does not match is taken out of the
   deployment, and a producer whose condition does not match loses its `@Produces` annotation.
2. the **registration** step collects the beans the container has registered, which is the complete bean graph
   of the deployment.
3. the **validation** step evaluates the conditions that asked for the bean graph again, now that the graph
   is complete, and reports a deployment problem when the answer changed.

The third step exists because the discovery step of a build compatible extension cannot enumerate the
classes of the deployment, so the extension collects them itself while it enhances them. The bean graph is
therefore incomplete while the conditions are evaluated, and a condition that depends on it may be decided
too early. When that happens the build fails with a message that names the element and the condition,
instead of deploying a bean that the conditions do not allow.

A condition of the CDI Lite path is evaluated against the classes the build has seen, not against the beans
the container has registered. A condition that asks for the beans of the deployment is therefore
order-sensitive, and the validation step is what makes the difference visible.

### Deliberate limitations

- **On Weld, the CDI Lite path cannot remove a class from the deployment.** Weld translates the enhancement
  step of a build compatible extension into a `ProcessAnnotatedType` event, and it decides that a class is a
  managed bean by its constructor and not by its annotations. A class whose annotations are taken away stays
  in the deployment, as a `@Dependent` bean without the scope it was declared with. A **producer** is
  removed properly, because the annotation that makes it a producer is taken away.
- **Synthetic beans are not covered.** `ProcessBeanAttributes` does not fire for beans added through
  `AfterBeanDiscovery.addBean()`, because they have no annotated class to carry a condition. An extension
  that adds a synthetic bean decides up front whether it should exist.
- **Alternative selection is not modelled.** An `@Alternative` bean counts as present even when it is not the
  selected alternative.
- **The model assumes `bean-discovery-mode="annotated"`.** In that mode a class without a bean-defining
  annotation is not a bean, and the extension treats it as absent. The mode is not observable from a
  portable extension, so an archive that uses `bean-discovery-mode="all"` reports its plain classes only
  once the container has processed them.
- **The model spans the whole deployment.** A bean in `/lib` is visible to a bean in a `WAR`. This mirrors
  the asymmetry that already exists in CDI bean access, rather than inventing a per-archive rule.
- **Conditions are evaluated at bootstrap only.** Selecting an implementation per HTTP request is a different
  problem and needs a different mechanism, such as interception or decoration.
- **Configuration comes from system properties and environment variables.** Jakarta Config is the intended
  long-term source; it is not ready yet, and that is a reason to keep the surface minimal.

### Failure semantics

Failing fast is deliberate - a silently disabled bean is far harder to diagnose than a startup error.

| Failure | Result |
|---|---|
| Condition class has no no-argument constructor | `DefinitionException` (CDI Full), `DeploymentException` (CDI Lite), naming the condition class |
| Condition constructor throws | the same exception, with the original cause |
| `Condition.matches(...)` throws | the same exception, with the original cause |
| A CDI Lite condition depends on the bean graph and the answer changed | a deployment problem naming the element and the condition |

## Proposal for jakartaee/cdi#986

> This section is the proposal that would accompany the prototype on
> [jakartaee/cdi#986](https://github.com/jakartaee/cdi/issues/986). It answers the questions that were raised
> in the discussion.

### The API

Three core types, modelled on Spring's `@Conditional` and Micronaut's `@Requires`, but expressed in CDI
terms only:

```java
@Conditional(Class<? extends Condition<?>>[] value())   // the annotation
Condition<A extends Annotation>                          // the SPI
ConditionContext                                         // the CDI-native view
}
```

`@Conditional` is repeatable, so several conditions may be declared on one element, one annotation each.
The mechanism needs a container annotation, and the container is named the way the Java ecosystem names
theirs: a top-level annotation in the plural form.

```java
@Conditionals(Conditional[] value())                  // the container
}
```

| Annotation | Container | Source |
|---|---|---|
| `@Location` | `@Locations` | CDI 4.1 |
| `@NamedQuery` | `@NamedQueries` | Jakarta Persistence |
| `@Schedule` | `@Schedules` | Jakarta EJB |
| `@JMSDestinationDefinition` | `@JMSDestinationDefinitions` | Jakarta JMS |
| `@ComponentScan` | `@ComponentScans` | Spring Framework |
| `@PropertySource` | `@PropertySources` | Spring Framework |
| `@Scheduled` | `@Schedules` | Spring Framework |
| `@JmsListener` | `@JmsListeners` | Spring Framework |
| `@Requires` | `@Requirements` | Micronaut |
| `@QueryHint` | `@QueryHints` | Micronaut Data |
| `@JoinColumn` | `@JoinColumns` | Micronaut Data |

Micronaut's `@Requires` is its own conditional annotation, so the closest analogue in the ecosystem names
its container the same way. Spring's `@Conditional` is not repeatable at all - Spring expresses several
conditions through composed meta-annotations instead - so of the two frameworks, only Micronaut has a
repeatable condition annotation.

The alternative shape is a nested `List`, used by Jakarta Validation (`@Pattern.List`), Jakarta Data
(`@Select.List`) and Micronaut (`@OrderBy.List`). Spring has a few one-off names of its own, `@SqlGroup`
and a nested `@ImportHttpServices.Container`. A top-level plural container is the shape used by most
specifications and by both frameworks, and it keeps the public API to one annotation more.

### When is the condition evaluated, and why there?

The condition is evaluated during `ProcessBeanAttributes`, and the bean is vetoed when it does not match.
That is the only portable point at which a discovered bean can still be removed. The alternative -
evaluating in `AfterBeanDiscovery` - would be too late: the bean would already be deployed, and CDI has no
portable way to withdraw it.

This answers the objection that a condition cannot be evaluated during bean discovery because the container
is not ready: the condition does not need the container. It receives a `ConditionContext`, and the only
container state it exposes is a deliberately restricted view.

### How does the bean set work, given that `getBeans` is not available at that point?

This is the sharpest question in the discussion, and it deserves a precise answer.

`BeanManager.getBeans(...)` is indeed **not** usable while the container is bootstrapping - Weld enforces
this with a container-state check, and `AfterBeanDiscovery` is the first point at which it becomes legal.
That is precisely why the prototype does **not** use `getBeans`.

Instead, the set of beans that could be part of the deployment is collected from the `ProcessAnnotatedType`
events. The container fires those for every discovered type before it fires the first
`ProcessBeanAttributes`, so the model is complete when the first condition is evaluated. Bean types are
derived from the annotated types following the rules of the specification, and are refined with the
container's own `BeanAttributes` as the deployment proceeds.

The result is the *potential bean set* described above: conditions never hide one another, and the answer
does not depend on the order in which beans are declared. Ordering controls such as Spring Boot's
`@AutoConfigureAfter` are therefore not needed.

The prototype verifies this against the container itself. `HasBeanAgreesWithContainerTest` asks the model
the same questions that `BeanManager.getBeans(...)` answers for qualified beans, named beans, `@Typed`
beans and producers, and asserts that the two agree - with exactly one documented difference: a bean that
is vetoed by a condition is still reported as present, because the model describes the beans that *could*
be part of the deployment.

### Which conditions should the specification define?

The API provides built-in conditions for common cases - property, class, and bean presence - each with an inverse counterpart, named after familiar Spring-style annotations. They are intentionally small and composable.

One difference from Spring is worth pointing out. Spring's class conditions take `Class<?>` values, and they
work because Spring reads the annotation metadata without loading the classes. CDI has no such reading: an
annotation instance is created by the container, and reading an attribute that refers to a class which is
not on the classpath throws `TypeNotPresentException`. A CDI specification would therefore have to name the
classes instead, or define another way of expressing the requirement.

### Should `@Conditional` be a stereotype?

Yes, and the prototype makes it one. In Spring, `@Conditional` is a meta-annotation: an application composes
its own annotations with it. The CDI counterpart of a composed annotation is the stereotype, so `@Conditional`
is declared as a `@Stereotype` and may be used as a meta-annotation.

This has a pleasant consequence: the container itself takes part. `Bean.getStereotypes()` reports
`@Conditional`, and a stereotype that declares `@Conditional` inherits it, exactly as CDI defines
stereotype inheritance. The condition is nevertheless evaluated by the extension, because the veto point is
still `ProcessBeanAttributes`.

### What about synthetic beans?

Not covered, and deliberately so. `ProcessBeanAttributes` does not fire for them, and an extension that adds
a synthetic bean is in a better position to decide whether it should exist at all.

### What about EAR and WAR modularity?

The model spans the whole deployment, so a bean in `/lib` is visible to a bean in a `WAR`. This mirrors
the asymmetry that already exists in CDI bean access, where a bean in `/lib` cannot see the beans of a `WAR`.
Introducing a per-archive rule for conditions only would create a second, inconsistent notion of bean
visibility.

### What about CDI Lite?

CDI Lite has no portable extensions, so the mechanism has to be different: the conditions are evaluated
while the application is built, by a build compatible extension.

The prototype implements that path in the `lite` module, and it has to work around a real limitation of
the specification: the discovery step of a build compatible extension cannot enumerate the classes of the
deployment, so the bean graph is not known while the conditions are evaluated. The prototype therefore
collects the classes while it enhances them, collects the registered beans afterwards, and evaluates the
conditions that depend on the bean graph one more time when the graph is complete. When the answer changed,
the build fails with a message that names the element and the condition.

A specification for CDI Lite would have to say more about this. The question it has to answer is whether a
condition that depends on the bean graph may be evaluated at all at build time, and what a container does
when the answer is not stable.

### What about a condition that needs the container?

A condition cannot inject beans, because at evaluation time the container is not able to create them. It
reads the deployment through `ConditionContext.hasBean(...)` (and class/property checks), not through bean instances. A condition that needs a bean instance must be modeled differently (for example, via producer or runtime logic).

### Is the name right?

`@Conditional` follows Spring, which is the most widely known spelling. Micronaut uses `@Requires`, and
DeltaSpike uses `@Exclude`. The three frameworks describe the same idea, and the question of whether CDI
should standardize on one of these names is worth a separate discussion.
