# Conditional Beans

A portable CDI extension that enables a bean **only when a condition matches the current deployment**.

- Target runtime: **CDI 4.1** (`jakarta.enterprise:jakarta.enterprise.cdi-api:4.1.0`)
- Verified on **Weld 6.0.3.Final** with **Weld JUnit5**
- Core API: **four types** — `@Conditional`, `@Conditionals`, `Condition`, `ConditionContext`
- Repeatable support: **one container** — `@Conditionals`, generated by the compiler
- Two runtimes: **CDI Full** (portable extension) and **CDI Lite** (build compatible extension)
- No runtime dependency beyond the CDI API

FluDa Conditional Beans is a working prototype for the Jakarta EE CDI issues
[jakartaee/cdi#869](https://github.com/jakartaee/cdi/issues/869) and
[jakartaee/cdi#986](https://github.com/jakartaee/cdi/issues/986).

Part of the [FluDa](https://fludakit.github.io/) toolkit — [module source](https://github.com/fludakit/conditional-beans).

## Modules

| Artifact | Package | What it is |
|---|---|---|
| `fluda-conditional-beans-api` | `io.github.fludakit.conditional` | Core API (`@Conditional`, `@Conditionals`, `Condition`, `ConditionContext`) and the built-in conditional annotations with their condition implementations. |
| `fluda-conditional-beans-full` | `io.github.fludakit.conditional.full` | CDI Full runtime: portable extension that evaluates conditions at bootstrap and vetoes non-matching beans and producers. |
| `fluda-conditional-beans-lite` | `io.github.fludakit.conditional.lite` | CDI Lite runtime: build compatible extension that evaluates conditions during build/enhancement with deferred validation. |

## How it works

A bean whose condition does not match is **not part of the deployment**:

- it is not injectable,
- it does not show up in `BeanManager.getBeans(...)`,
- it produces no `ProcessBean` event.

An injection point that requires a vetoed bean fails the deployment with an unsatisfied-dependency error. A missing bean is therefore explicit, instead of silently degrading to a no-op at runtime.

The extension is registered through `META-INF/services/jakarta.enterprise.inject.spi.Extension`, so it is active in every deployment that has the artifact on the classpath.

## The API

### `@Conditional`

```java
@Documented
@Retention(RUNTIME)
@Target({ TYPE, METHOD, FIELD, ANNOTATION_TYPE })
@Stereotype
@Repeatable(Conditionals.class)
public @interface Conditional {
    Class<? extends Condition<?>>[] value();
}
```

It may be placed on a bean class, a producer method or a producer field.

The annotation is **repeatable**, so several conditions can be declared on one element, one annotation each:

```java
@ApplicationScoped
@Conditional(ChinaCondition.class)
@Conditional(DatabaseAvailable.class)
public class ChinaTaxCalculator implements TaxCalculator {
}
```

The array form carries the same meaning, and the two styles may be mixed — `@Conditional({ A.class, B.class })` and two separate `@Conditional` annotations are collected together, and **all of them have to match**.

A condition declared on a **stereotype** is collected in addition to the ones declared on the bean, which is why a stereotype may add its own requirements without interfering with the bean.

The annotation is itself a **CDI stereotype** and may be used as a meta-annotation, which is how an application composes an annotation of its own.

### `@Conditionals`

The container annotation required by the repeatable annotation mechanism of Java. The compiler generates it and fills it with the annotations that were written. It is not meant to be used directly — declaring several `@Conditional` annotations is enough — and it stays invisible in the deployment: a bean that declares several conditions reports the same stereotypes as one that declares a single condition.

### `Condition`

```java
@FunctionalInterface
public interface Condition<A extends Annotation> {
    boolean matches(ConditionContext context, A annotation);
}
```

A condition is a plain class with a public no-argument constructor. It is instantiated by the container, not managed by CDI, and should be deterministic and side-effect free.

A condition is **written against the annotation that declares it**, so that it can read the values of that annotation without reflection:

```java
public class ChinaCondition implements Condition<ConditionalOnCountry> {

    @Override
    public boolean matches(ConditionContext context, ConditionalOnCountry annotation) {
        return "CN".equals(context.getProperty(annotation.country()).orElse(null));
    }
}
```

The type argument decides which annotation the condition is handed:

| The condition is written as | It is handed | The condition was declared by |
|---|---|---|
| `Condition<Conditional>` | the `@Conditional` annotation | `@Conditional(X.class)` on the bean |
| `Condition<ConditionalOnProperty>` | the `@ConditionalOnProperty` annotation | `@ConditionalOnProperty(...)` on the bean |
| `Condition<MyOwnAnnotation>` | the `@MyOwnAnnotation` annotation | an annotation of the application that carries `@Conditional` |

The choice is made by the type of the condition, so it is checked by the compiler and it stays consistent for every evaluation.

### `ConditionContext`

A read-only view of the deployment data available during evaluation. It exposes only what a bootstrap-time activation decision needs:

| Method | What it answers |
|---|---|
| `getProperty(String key)` | the value of a configuration property. A dotted key is also matched in a relaxed environment-variable form, so `app.country` and `APP_COUNTRY` both resolve. |
| `hasClass(String... className)` | whether all named classes are available to the deployment. |
| `hasBean(Class<?> beanClass, Class<? extends Annotation>... qualifiers)` | whether a bean of the given type and qualifiers is part of the deployment. |

`hasBean` answers from the **potential deployment model**: the answer never depends on declaration order, and a bean that is later vetoed by a condition still counts as present for evaluation purposes.

## Built-in conditions

| Annotation | The bean is enabled when |
|---|---|
| `@ConditionalOnBean(T.class)` | every named bean type has a bean in the deployment. |
| `@ConditionalOnMissingBean(T.class)` | every named bean type has **no** bean in the deployment. |
| `@ConditionalOnClass(Foo.class)` or `@ConditionalOnClass(name = "...")` | every named class is on the classpath. |
| `@ConditionalOnMissingClass(name = "...")` | every named class is **absent** from the classpath. |
| `@ConditionalOnProperty(name = "...", havingValue = "...")` | the configuration entry is present, and has the expected value when `havingValue` is set. |
| `@ConditionalOnMissingProperty(name = "...")` | the named configuration entries are **absent**. |

!!! note "Classes are named, not referenced"
    `@ConditionalOnClass` accepts a fully qualified **name** as well as a class literal. In CDI an annotation cannot safely refer to a class that is absent: the annotation instance is created, but reading the attribute throws `TypeNotPresentException`. A name is resolved without loading the class, which is what makes the check possible at all.
